## Admin authentication / OTP

Confirmed from source:
- Server-side admin data routes validate the Supabase user, active admin membership, and the OTP session cookie.
- The OTP challenge is hashed, short-lived, one-time, and consumed atomically through a database RPC once the migration exists.
- OTP is sent to the restricted Telegram admin group. All group members can read it, so membership is part of the security boundary.
- The HTML help text previously contradicted the implementation by saying the OTP was sent to private chat. This mismatch has been corrected in the PR branch and a regression test was added.
- CAPTCHA is not implemented yet.
- Failed email/password attempts are not yet sent to Telegram because password authentication still happens directly against the Supabase Auth endpoint from the browser. A server-side login gateway with verified CAPTCHA and abuse/rate limiting is required before claiming failed-login audit coverage.
- The trusted numeric Telegram user mapping has not been verified/seeded.
- Direct-Data-API bypass behavior and the migration have not been tested against a non-production database.

## Release blockers (ordered)

### Critical / release-blocking
1. Add server-side CAPTCHA verification to login and configure the provider keys for Preview and Production.
2. Move password authentication behind a server-side login endpoint so invalid login attempts can be audited without a spoofable client-only notification endpoint. Add durable rate limiting and privacy-aware audit records.
3. Apply the OTP migration to an isolated non-production Supabase environment, test RLS and direct Data API bypass, and verify challenge expiry/attempt limits/replay/logout/session invalidation.
4. Configure and verify the trusted Telegram numeric user mapping and real group delivery in Preview.
5. Run the full required CI suite on the latest PR head, not just a prior SHA.
6. Complete public website/catalog compatibility metadata integration without changing the approved visual design.

### High
1. Obtain clean Debian 13 install/launch/upgrade/uninstall evidence and native Qt tests before raising Sorot's Debian status.
2. Keep Arch status unverified until a native package artifact and lifecycle tests exist; do not enable the pacman adapter prematurely.
3. Review Supabase Auth leaked-password protection with the project owner and enable it after assessing user impact.
4. Establish required branch protection/status checks for `main`, after verifying the desired workflow names.

### Medium
1. Evaluate the two unused indexes using real query plans and workload history before deciding whether to retain or remove them.
2. Verify preview/prod environment parity by variable names and targets without exposing secret values.
3. Document release provenance/attestation only if the configured build infrastructure actually generates verifiable attestations.

## Release decision

**Do not merge PR #40 into `main` yet and do not deploy production from it.** GitHub CI was green on the last fully checked revision, but this change alters the admin dashboard to depend on server routes and OTP tables that do not exist in the live database yet. Merging would risk breaking admin access and would not meet the requested release gates. Resume after the non-production migration, server-side CAPTCHA/login audit, integration tests, and latest-head CI are complete.
