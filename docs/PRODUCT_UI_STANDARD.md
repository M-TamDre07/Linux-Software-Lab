# Product catalogue and detail-page UI standard

This is the shared, user-facing UI pattern contract for Linux Software Lab product pages. It records the existing catalogue style that the maintainer has approved; it is not a request to redesign each application.

## Canonical catalogue card

The canonical application list is `/software/`. Cards are generated by the shared `cardMarkup()` renderer in `public/assets/js/site.js` from `public/data/software.json`. New applications must be added to the data source instead of introducing a product-specific card renderer. The renderer already handles the icon, preview, category, release status, tags, platform, detail link, source link, and release link.

The shared visual rules live in `public/assets/css/site.css` and `public/assets/css/experience.css`, including `.software-card`, `.software-preview`, status badges, tags, and responsive layouts.

## Product detail pages

Use the existing classes and component structure:

- `.detail-hero`, `.detail-layout`, and `.detail-copy` for the product introduction.
- `.detail-title-row` and `.detail-icon` for product identity.
- `.detail-art`, `.detail-art-top`, and `.detail-art-caption` for clearly labelled product imagery.
- `.detail-body-grid` and `.detail-spec` for product information and status.
- Existing `.install-panel`, `.terminal-note`, and status patterns for installation and release readiness.

Every detail page must load the same base and experience stylesheets, state the actual development/release status, and accurately label concept artwork. Product-specific branding assets may differ; hierarchy, card geometry, spacing, status patterns, responsive behavior, keyboard focus, and light/dark theme behavior should remain shared.

## Release and compatibility states

- A download link is allowed only when a real artifact exists and its target format is known.
- A planned target (for example, Arch Linux for Sorot 0.6.0) is a status message, not a download card.
- Do not show a package-manager command for a distro without a matching package or build recipe that has actually been tested.
- Installation instructions must distinguish a development/source workflow from a published user release.
- Preserve each existing visual pattern unless a maintainer explicitly approves a change. Add regression tests when changing shared components.

## Acceptance checks

The website test suite should catch product pages that drift away from shared CSS, the catalogue page that stops using the common card renderer, invalid download metadata, a false claim about a distro package, or mismatches between an archived release manifest and website download metadata.
